# Ассортимент

Анализ каталога vs-travel.ru внутри MBOX: какие туры конфликтуют («свой против партнёрского»), где перебор по направлению, что завели со вчера. Экран — карточка «Ассортимент» в инструментах (`tab:tool:assortment`). Задача #518, исходный Python-анализатор — задача #498.

## Как устроено

| Файл | Что делает |

| `server/assortment-performance.mjs` | Результативность по местам: статус тура, заполнение архива и глубины, сезонный профиль, мёртвые сезоны, давность последней продажи, концентрация, сезонность по месяцам, свой продукт агрегатами. Чистые функции. |
| `server/assortment-sales-import.mjs` | Приём выгрузки CRM (книга Excel или CSV) → нормализованный фид заездов. Временный адаптер: ждём перевода продаж на API. |

## Данные

Таблицы создаются при запуске (`ensureAssortment`): `assortment_snapshots` (по снимку на день, хранятся 60 дней), `assortment_feedback`, `assortment_exclusions`, `assortment_sales`, `assortment_state` (выученное, журнал, последнее обновление), `assortment_shares`, `assortment_share_sessions`, `assortment_chat_messages`. При первом запуске один раз кладутся решения владельца, принятые до переноса: правило «вне анализа» для авторских туров Чекмарева и Слезкина и первые оценки (`server/assortment-seed.json`).

Каталог берётся с `https://vs-travel.ru/ajax/tour-search` (100 туров на страницу, параметр `p`). Снимок принимается, только если собрано ровно `totalHits` туров без повторов, иначе остаётся прежний. Сбой обновления не ломает экран: показывается время последнего удачного снимка. `ASSORTMENT_AUTORUN=0` отключает ежедневное обновление.

## Продажи: что продаётся, а что занимает место

Продажи приходят **выгрузками из CRM** и считаются **в местах**: «продано» — занятые места в дате (в архиве колонка «Отправлено», в глубине «Продано»). Выручки и цен в выгрузках нет.

- **Архив** — прошедшие даты, **глубина** — выставленные вперёд. Точка слияния (последний день архива) — решение владельца, `2026-10-21`; хранится в `assortment_state.sales_period`. Давность последней продажи считается от неё. Заполнение архива и глубины между собой не сравнивают: в глубине видны только текущие брони.
- **Статус тура**: `core` «Ядро: 21+», `working` «Рабочий: 6-20», `weak` «Слабый: 1-5 мест», `remove` «Убрать из продажи» (ноль продаж, прошедшие даты были, даты вперёд есть), `fresh` «Новый: нет истории» (прошедших дат нет), `gone` «Уже снят» (ноль продаж, дат вперёд нет).
- **Сезоны** считаются только по архиву. Сезонный профиль — сезон, на который приходится 60% и больше архивных продаж, иначе «Круглый год». Мёртвый сезон — не меньше трёх прошедших дат в сезоне при нуле продаж, когда сам тур продаётся.
- **Свой продукт** приходит отдельной выгрузкой и только построчно по турам (мест всего, продано, заполнение, доля заполнения глубины). Разбивки мест на архив и глубину, дат продаж и сезонов в ней нет, поэтому эти поля у своего продукта `null`, а сравнение с партнёрским корректно только по общему заполнению. Это временно: **ждём перевода продаж на API**, тогда свой продукт пойдёт теми же заездами и таблица `assortment_sales_own` уйдёт.
- **Сопоставление с каталогом.** Номера туров общие: у всех сведённых туров названия совпадают точно (проверено 22.10.2026 на выгрузке владельца — 685 совпадений, расхождений в названиях нет). Не сводятся туры, которых нет в текущем каталоге: почти все они без дат впереди, а сайт показывает то, что продаётся сейчас. Смотреть стоит на несведённые туры с датами впереди — они продаются, а карточки на сайте нет. Ненайденные туры перечисляются поимённо (`matching`, `unmatched`, лист «Нет в каталоге»), их продажи не участвуют в анализе конфликтов, направлений и дублей, но в сводных цифрах по местам учтены. Карточкам каталога, которых нет в выгрузке, нулевые продажи не приписываются (`no_data`, лист «Без данных»).
- **Дубли с учётом продаж.** Лидером группы близких дублей остаётся тур с большими продажами, при равных продажах — с лучшим заполнением архива. В обоснованиях пишется, сколько продано, какое заполнение и когда была последняя продажа. Нулевые туры автоматически не снимаются: в отчёте есть кнопка «Скрыть без продаж» (решение владельца 22.10).

Загрузка: `assortment_import_sales_dates` (владелец) или `POST /api/mbox/assortment/sales/import` — книга Excel в base64 либо CSV. Выгрузка заменяется целиком: догрузка частями путает заполнение. Чтение: `assortment_performance`, `assortment_sales_tours`, `assortment_tour_sales`, `assortment_sales_sources`.

## Отчёт для сотрудников и выключатель рекомендаций

Книга Excel собирается из тех же данных, что и отчёт на экране (`reportData`), поэтому цифры всегда совпадают: `assortment_export_xlsx` или `GET /api/mbox/assortment/export.xlsx`.

Состав отчёта — один выключатель `view.advice`:

- у владельца кнопка на экране (`POST /api/mbox/assortment/view`), значение в `assortment_state.view`;
- у каждой ссылки и логина свой столбец `advice` (ссылки различаются по праву × чат × рекомендации);
- складываются по самому строгому: ссылка не может вернуть себе рекомендации, если владелец их выключил.

При «без рекомендаций» уходят «Что делать», кандидаты на снятие, советы по группам и `cut_candidates` направлений, а статус тура пишется фактом («Без продаж, даты впереди есть» вместо «Убрать из продажи»). Цифры, конфликты и направления остаются как есть. Листы «Убрать сейчас» и «Что делать» в книгу не попадают.

## Сходимость с Python-эталоном

`server/assortment-engine.test.mjs` сравнивает данные отчёта целиком (конфликты, серьёзность, направления, группы, выводы, рекомендации, хэши) с эталоном, снятым с Python-версии на реальном снимке каталога от 20.10.2026 (835 туров): с продажами и без, сравнение двух снимков в обе стороны, порядок туров на входе не влияет. `assortment-learn.test.mjs` сверяет самообучение (приём и отклонение). Фикстуры — `server/fixtures/assortment/`.

Нюансы порта, о которые легко споткнуться: `\b` и `\w` в JavaScript не понимают кириллицу (`pyRegex`), `round()` в Python округляет по точному двоичному значению и к чётному (`pyRound`), `json.dumps` Python ставит `, ` и `: ` и экранирует не-ASCII (`pyDumps`, от него зависят хэши).

## Доступ по ссылке и паролю

Как у SEO Wizard (`server/seo-share.mjs`), плюс выбор состава. У каждой ссылки и логина два выбора:

- права: **просмотр** (читает) или **управление** (ставит оценки, выводит туры из анализа, обучает инструмент);
- состав: **только инструмент** или **инструмент + чат с агентом**.

Ссылок до четырёх (права × чат), логинов сколько нужно. Белый список вызовов — `isAllowed` в `assortment-share.mjs`: отчёт, состояние, инструменты (какие — решает уровень доступа), оценки (только управление) и чат (только если выдан). Обновление каталога с сайта, настройки, ссылки, продажи и сброс выученного по ссылке недоступны никогда. Смена пароля, прав или чата закрывает открытые сессии логина; ссылку можно заменить или отключить. После пяти неверных паролей вход замедляется.

Отчёт открывается в изолированной рамке (`sandbox` без `allow-same-origin`): у страницы нет доступа к cookie, она просит окно-хозяин сохранить оценку через `postMessage`. Данные каталога (названия туров от партнёров) поэтому не могут украсть сессию.

### Чат с агентом

Это не общий чат MBOX. Агент работает только с инструментами ассортимента на уровне доступа ссылки (в просмотре записывающих инструментов у него нет), не видит проекты, заметки и ключи, отвечает через модели Джарвиса (`GEMINI_API_KEY`, запасная `GROQ_API_KEY`; на проде обе доступны). Лимиты: 20 вопросов в час и 120 в сутки на ссылку, сообщение до 1500 знаков, один ответ за раз в одном чате. Нет ключей модели — чат честно пишет «агент недоступен». История лежит в `assortment_chat_messages`, владелец видит число вопросов у каждой ссылки.

## Инструменты агента и навык

MCP-сервер (`scripts/mbox-mcp-server.mjs`) регистрирует инструменты `assortment_*` по описаниям из `assortment-tool-defs.mjs` и пересылает вызовы на `POST /api/mbox/assortment/tool`. Облачные агенты (ClaudeCloud, CodexCloud) получают их после `bash /opt/mbox/deploy/cloud-agents/install.sh` и `systemctl restart mbox-cloud-claude mbox-cloud-codex`.

Навык `assortment` (`skills/assortment/`) серверный Claude может улучшать на лету: `edit_skill_file` / `write_skill_file` (история правок сохраняется), записи о причинах — `skill_learning_add` (`learnings.md` навыка). Принципы самого анализа, которые объясняет владелец, — отдельно: `assortment_record_learning` (журнал выученного в базе, `assortment_learnings`). В репозиторий правки навыка возвращает `npm run mbox:skills-pull`.

## Решения владельца, которые нельзя забывать

- Похожие карточки («- 2», «- 3», сезоны, отели) объединять и снимать нельзя: группы вариантов — справка, рекомендаций «снять» по ним нет, «лишних карточек» не считаем (20.10.2026).
- Тур без продаж из анализа сам не выкидывается: вместо автосноса кнопка «Скрыть без продаж» (22.10.2026).
- Дубли разбираются с учётом продаж: лидер — по проданным местам, при равенстве — по заполнению архива (22.10.2026).
- Данные из таблицы — временное решение, ждём перевода продаж на API (22.10.2026).
- Что не сопоставилось с каталогом — писать честно списком, а не прятать, и отделять «тур уже не продаётся» от «продаётся, а карточки нет» (22.10.2026).
- Свой тур не снимается никогда; рекомендация «что снять» осторожная, снимается только близкий дубль.
- Цены в у.е.; событийные туры сравниваются только с турами на тот же праздник; тур с одной датой судится только по своей дате.

Полный список с датами и причинами — `server/assortment-learnings-seed.md` (стартовый журнал) и `skills/assortment/rules.md`.

## Проверка и выкладка

- `node --test server/assortment-*.test.mjs` — движок, самообучение, доступ, чат (мок), планировщик, результативность и выгрузка.
- `server/assortment-performance.test.mjs` — сходимость с эталонной книгой владельца «Ассортимент_продажи.xlsx» (пять выгрузок CRM, 21 839 заездов, 1 280 туров): статус, места, даты, заполнение, месяцы с продажами, первая и последняя продажа, давность, сезонные суммы, сезонный профиль, мёртвые сезоны, цифры по отделам и концентрация совпадают с листом «Все туры» и «Сводкой» до знака. Фикстуры — `fixtures/assortment/sales-dates.json.gz` и `sales-reference.json.gz`.
- Сквозной сценарий (база, оценки, правила, обучение, ссылки, логины, сессии, отзыв) прогнан на настоящем Postgres в виде PGlite: SQL проверен вне боевой базы.
- После выкладки: открыть «Инструменты → Ассортимент», создать ссылку «только инструмент» и открыть её в приватном окне; вызвать `assortment_summary` из MCP.
- Откат: ветка `feature/assortment` целиком; таблицы `assortment_*` отдельные, остальной MBOX их не читает.
